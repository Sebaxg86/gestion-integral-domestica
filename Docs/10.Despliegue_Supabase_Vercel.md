# Despliegue del MVP 0

## Objetivo

Este documento describe cómo enlazar GID con Supabase y Vercel sin guardar
secretos en el repositorio. Las migraciones SQL son la fuente de verdad de la
base de datos y Vercel compila la aplicación ubicada en `apps/web`.

## Requisitos locales

- Node.js `22.13.0` o posterior dentro de la rama 22 LTS.
- pnpm `10.34.5`.
- Sesión iniciada en las CLI de Supabase y Vercel.
- Un proyecto de Supabase y uno de Vercel.

Nunca pegues contraseñas, access tokens, service role keys ni el secreto del
cron en una conversación, commit, captura o ticket.

## Supabase

### 1. Iniciar sesión y enlazar

```bash
npx supabase@latest login
npx supabase@latest link --project-ref TU_PROJECT_REF
```

La contraseña de base se escribe únicamente en la terminal cuando la CLI la
solicita.

### 2. Aplicar y comprobar la base

```bash
npx supabase@latest db push
npx supabase@latest db lint --linked --level warning --fail-on error
npx supabase@latest test db --linked
```

Antes de confirmar una migración destructiva futura se requiere respaldo y un
procedimiento específico. El MVP inicial solo agrega esquema.

### 3. Desplegar funciones

```bash
npx supabase@latest functions deploy finalize-document
npx supabase@latest functions deploy replace-document-file
npx supabase@latest functions deploy cleanup-files --no-verify-jwt
npx supabase@latest functions deploy process-reminders --no-verify-jwt
```

Configura los secretos directamente desde una terminal local:

```bash
openssl rand -hex 32
openssl rand -hex 32
npx supabase@latest secrets set APP_URL=https://TU_DOMINIO CRON_SECRET=PRIMER_VALOR FILE_CLEANUP_SECRET=SEGUNDO_VALOR
```

`SUPABASE_URL`, `SUPABASE_ANON_KEY` y `SUPABASE_SERVICE_ROLE_KEY` son secretos
reservados que Supabase expone automáticamente a sus Edge Functions. La service
role key nunca se configura en Vercel ni se envía al navegador.

### 4. Programar recordatorios

En Supabase Dashboard abre `Integrations > Cron`, crea un trabajo cada cinco
minutos y configura una solicitud `POST` a:

```text
https://TU_PROJECT_REF.supabase.co/functions/v1/process-reminders
```

La solicitud debe enviar `Authorization: Bearer CRON_SECRET`. Guarda el valor
mediante Vault o el mecanismo de secretos del panel; no lo escribas dentro de
una migración. Ejecuta una prueba manual y confirma que la respuesta sea
`{"processed": 0}` cuando no existan recordatorios pendientes.

Crea un segundo trabajo cada hora que invoque `cleanup-files` con
`Authorization: Bearer FILE_CLEANUP_SECRET`. El proceso elimina cargas
abandonadas y binarios sustituidos después de 24 horas, pero conserva sus
metadatos técnicos.

### 5. Autenticación

En `Authentication > URL Configuration` registra:

- URL del sitio: dominio de producción de Vercel.
- Redirect local: `http://localhost:3000/auth/callback`.
- Redirect de producción: `https://TU_DOMINIO/auth/callback`.

Mantén activa la confirmación de correo. Configura en producción un proveedor
SMTP transaccional antes de invitar usuarios reales.

## Vercel

### 1. Enlazar el proyecto

```bash
npx vercel@latest login
npx vercel@latest link
```

En el proyecto de Vercel selecciona:

- Framework: Next.js.
- Root Directory: `apps/web`.
- Node.js: rama 22.x compatible con `>=22.13.0`.

Vercel detectará el workspace pnpm desde la raíz del repositorio y resolverá
los paquetes `@gid/*` utilizados por la aplicación.

### 2. Variables públicas

Configura para `Development`, `Preview` y `Production` según corresponda:

```text
NEXT_PUBLIC_APP_URL
NEXT_PUBLIC_SUPABASE_URL
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY
```

La publishable key está diseñada para el navegador; la seguridad de datos sigue
dependiendo de RLS. No agregues `SUPABASE_SERVICE_ROLE_KEY` a Vercel.

### 3. Desplegar

```bash
npx vercel@latest deploy
npx vercel@latest deploy --prod
```

El primer comando crea una vista previa. Promueve a producción solamente después
de probar registro, confirmación de correo, carga privada y aislamiento entre dos
cuentas de prueba.

## Comprobaciones posteriores

1. Crear y verificar dos cuentas sintéticas.
2. Crear una familia y vivienda en cada cuenta.
3. Confirmar que ninguna cuenta puede leer UUID de la otra.
4. Cargar un PDF de prueba y verificar que el bucket no sea público.
5. Confirmar que una URL firmada deja de funcionar después de cinco minutos.
6. Crear un recordatorio vencido y ejecutar el cron dos veces.
7. Verificar que exista una sola notificación.
8. Instalar la PWA en un teléfono compatible.
9. Revisar logs sin correos completos, notas, números documentales ni URLs
   firmadas.

## Restauración

Antes del piloto debe documentarse y ejecutarse una restauración real en un
proyecto aislado. El objetivo inicial es `RPO <= 24 horas` y `RTO <= 8 horas`.
La prueba debe incluir tablas y objetos privados, no solo PostgreSQL.
