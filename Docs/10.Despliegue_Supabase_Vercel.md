# Despliegue del MVP 0

## Objetivo

Este documento describe cómo enlazar GID con Supabase y Vercel sin guardar
secretos en el repositorio. Las migraciones SQL son la fuente de verdad de la
base de datos y Vercel compila la aplicación ubicada en `apps/web`.

## Entorno conectado

El entorno de producción vigente es:

- Supabase: proyecto `gestion-integral-domestica` en `us-east-2`.
- Project ref: `npzmapwfqdvdsscgsarf`.
- URL de Supabase: `https://npzmapwfqdvdsscgsarf.supabase.co`.
- Vercel: proyecto `gid-web` con Root Directory `apps/web`.
- URL de producción: `https://gid-web-mu.vercel.app`.

Estos identificadores y URLs son públicos. Las claves privadas y los secretos de
automatización no se documentan ni se versionan.

## Requisitos locales

- Node.js `22.13.0` o posterior dentro de la rama 22 LTS.
- pnpm `10.34.5`.
- Sesión iniciada en las CLI de Supabase y Vercel.
- Un proyecto de Supabase y uno de Vercel.

Nunca pegues contraseñas, access tokens, service role keys ni el secreto del
cron en una conversación, commit, captura o ticket.

## Supabase

### 1. Iniciar sesión y enlazar

```bash
npx supabase@latest login
npx supabase@latest link --project-ref npzmapwfqdvdsscgsarf
```

La contraseña de base se escribe únicamente en la terminal cuando la CLI la
solicita.

### 2. Aplicar y comprobar la base

```bash
npx supabase@latest db push
npx supabase@latest db lint --linked --level warning --fail-on error
npx supabase@latest test db --linked supabase/tests/database
```

La orden `test db` utiliza Docker como cliente auxiliar. Si Docker no está
disponible, el mismo archivo puede ejecutarse sin persistir sus datos mediante:

```bash
npx supabase@latest db query --linked --file supabase/tests/database/rls_isolation.test.sql
```

Antes de confirmar una migración destructiva futura se requiere respaldo y un
procedimiento específico. El MVP inicial solo agrega esquema.

### 3. Desplegar funciones

```bash
npx supabase@latest functions deploy --project-ref npzmapwfqdvdsscgsarf --use-api
```

Configura los secretos directamente desde una terminal local:

```bash
npx supabase@latest secrets set APP_URL=https://gid-web-mu.vercel.app
```

`CRON_SECRET` y `FILE_CLEANUP_SECRET` deben generarse con al menos 32 bytes
aleatorios. El mismo valor de cada secreto se guarda como secreto de la función
Edge y, cifrado, en Vault bajo `gid_cron_secret` y `gid_cleanup_secret`. Vault
también contiene `gid_project_url`. No imprimas los valores ni los escribas en
un archivo versionado.

`SUPABASE_URL`, `SUPABASE_ANON_KEY` y `SUPABASE_SERVICE_ROLE_KEY` son secretos
reservados que Supabase expone automáticamente a sus Edge Functions. La service
role key nunca se configura en Vercel ni se envía al navegador.

### 4. Programar recordatorios

La migración `202607310005_scheduled_jobs.sql` mantiene dos trabajos activos:

- `gid-process-reminders`: cada cinco minutos.
- `gid-cleanup-files`: cada hora, en el minuto 17.

Los trabajos obtienen URL y credenciales desde Vault e invocan las funciones
Edge mediante `pg_net`. El proceso de limpieza elimina cargas abandonadas y
binarios sustituidos después de 24 horas, pero conserva sus metadatos técnicos.
Después de rotar un secreto hay que actualizar tanto el secreto Edge como su
valor correspondiente en Vault.

### 5. Autenticación

En `Authentication > URL Configuration` registra:

- URL del sitio: `https://gid-web-mu.vercel.app`.
- Redirect local: `http://localhost:3000/auth/callback`.
- Redirect de producción: `https://gid-web-mu.vercel.app/auth/callback`.

Mantén activa la confirmación de correo. Configura en producción un proveedor
SMTP transaccional antes de invitar usuarios reales.

### 6. Acceso con Google y Apple

Ambos proveedores utilizan el callback administrado por Supabase:

```text
https://npzmapwfqdvdsscgsarf.supabase.co/auth/v1/callback
```

Para Google crea un cliente OAuth de tipo `Web application` y registra:

- Origen JavaScript: `https://gid-web-mu.vercel.app`.
- Origen local: `http://localhost:3000` mientras se desarrolla.
- Redirect autorizado: el callback de Supabase indicado arriba.
- Scopes: `openid`, `userinfo.email` y `userinfo.profile`.

Guarda el Client ID y Client Secret directamente en
`Authentication > Sign In / Providers > Google`. No deben agregarse a Vercel ni
al repositorio.

Para Apple se requiere una cuenta de Apple Developer, un App ID con la capacidad
Sign in with Apple, un Services ID web y una signing key. En el Services ID usa:

- Dominio: `npzmapwfqdvdsscgsarf.supabase.co`.
- Return URL: el callback de Supabase indicado arriba.

El Services ID debe ocupar el primer lugar en Client IDs dentro del proveedor
Apple de Supabase. El client secret firmado de Apple vence como máximo cada seis
meses; programa su rotación y conserva el archivo `.p8` fuera del repositorio.

Después de habilitar cada proveedor, confirma públicamente su estado con
`/auth/v1/settings` y prueba autorización, cancelación, callback, creación del
perfil y redirección a onboarding.

## Vercel

### 1. Enlazar el proyecto

```bash
npx vercel@latest login
npx vercel@latest link --project gid-web --yes
```

En el proyecto de Vercel selecciona:

- Framework: Next.js.
- Root Directory: `apps/web`.
- Install Command: `pnpm install --frozen-lockfile`.
- Build Command: `pnpm build`.
- Output Directory: `.next`.
- Node.js: rama 22.x compatible con `>=22.13.0`.

Vercel detectará el workspace pnpm desde la raíz del repositorio y resolverá
los paquetes `@gid/*` utilizados por la aplicación.

### 2. Variables públicas

Configura para `Development`, `Preview` y `Production` según corresponda:

```text
NEXT_PUBLIC_APP_URL
NEXT_PUBLIC_SUPABASE_URL
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY
```

La publishable key está diseñada para el navegador; la seguridad de datos sigue
dependiendo de RLS. No agregues `SUPABASE_SERVICE_ROLE_KEY` a Vercel.

### 3. Desplegar

```bash
npx vercel@latest deploy
npx vercel@latest deploy --prod
```

El primer comando crea una vista previa. Promueve a producción solamente después
de probar registro, confirmación de correo, carga privada y aislamiento entre dos
cuentas de prueba.

La producción actual está publicada en `https://gid-web-mu.vercel.app`.

## Restauración

Antes del piloto debe documentarse y ejecutarse una restauración real en un
proyecto aislado. El objetivo inicial es `RPO <= 24 horas` y `RTO <= 8 horas`.
La prueba debe incluir tablas y objetos privados, no solo PostgreSQL.
