# Arquitectura y stack del MVP 0

## Estado de la decisión

**Estado:** Aceptada

**Fecha:** 31 de julio de 2026

**Alcance:** MVP 0 de GID — Gestión Integral Doméstica

## 1. Contexto

GID es una PWA mobile-first que administra familias, viviendas, documentos,
archivos privados, vencimientos y notificaciones. La arquitectura debe priorizar:

- Aislamiento comprobable entre familias.
- Integridad relacional y operaciones idempotentes.
- Almacenamiento privado de archivos.
- Una experiencia instalable y rápida en navegadores modernos.
- Entrega incremental sin construir infraestructura innecesaria.
- Portabilidad razonable de datos y lógica crítica.

## 2. Decisión

Se adopta TypeScript de extremo a extremo con Next.js para la aplicación y
Supabase como plataforma administrada de backend.

| Área | Decisión |
| --- | --- |
| Frontend y PWA | Next.js App Router, React y TypeScript estricto |
| Estilos | Tailwind CSS y variables CSS derivadas del sistema de Figma |
| Primitivas accesibles | Radix UI solo donde aporte comportamiento complejo |
| Formularios | React Hook Form y Zod |
| Estado remoto interactivo | TanStack Query donde se requiera caché u optimismo |
| Base de datos | PostgreSQL administrado por Supabase |
| Identidad | Supabase Auth |
| Autorización | PostgreSQL Row Level Security |
| Archivos | Buckets privados de Supabase Storage |
| Trabajos programados | `pg_cron`, funciones SQL y Supabase Edge Functions |
| PWA | Manifest de Next.js, service worker y Web Push progresivo |
| Pruebas | Vitest, Testing Library, Playwright y pruebas SQL/RLS |
| Workspace | pnpm workspaces |
| Hosting web | Vercel |
| CI | GitHub Actions |

## 3. Límites de arquitectura

### 3.1 Aplicación web

Next.js es responsable de:

- Renderizar rutas públicas y autenticadas.
- Mantener layouts responsive y estados de carga o error.
- Ejecutar operaciones del usuario con su sesión activa.
- Emitir URLs firmadas de corta duración cuando corresponda.
- Servir el manifest, service worker y recursos de la PWA.

Los Server Components se utilizarán para lecturas iniciales. Los Client
Components quedarán limitados a interacción, APIs del navegador y estado local.

### 3.2 PostgreSQL y RLS

PostgreSQL es responsable de:

- Integridad referencial y restricciones de dominio.
- Aislamiento entre familias mediante RLS.
- Atomicidad de operaciones que afectan varias tablas.
- Idempotencia de recordatorios y notificaciones.
- Timestamps efectivos asignados por servidor.

Las migraciones SQL son la fuente de verdad. No se adopta un ORM durante el MVP
0 porque RLS, funciones, triggers y constraints son parte central del diseño.

### 3.3 Archivos

- Los archivos se almacenan en un bucket privado.
- La ruta física utiliza identificadores opacos y nunca datos personales.
- La autorización del documento se comprueba antes de firmar una descarga.
- Tamaño, extensión declarada y firma de contenido se validan en servidor.
- Un archivo rechazado se elimina y no queda accesible.

### 3.4 Recordatorios

`pg_cron` invoca una Edge Function programada. La función ejecuta una operación
transaccional e idempotente respaldada por constraints únicos. Repetir el trabajo
no puede generar una segunda notificación para el mismo recordatorio y receptor.

## 4. Estrategia PWA

El MVP incluye:

- Manifest instalable.
- Iconos y modo `standalone`.
- Shell y recursos estáticos con caché segura.
- Detección de conexión y recuperación explícita.
- Preparación para Web Push.

No se promete sincronización offline de escrituras. Una pérdida de conexión
conserva el formulario en memoria, informa el error y permite reintentar.

## 5. Seguridad

- El navegador solo recibe variables públicas de Supabase.
- La service role key nunca usa el prefijo `NEXT_PUBLIC_`.
- Toda tabla expuesta habilita RLS antes de recibir datos.
- Las políticas se prueban con usuarios de familias distintas.
- Los buckets son privados por defecto.
- Las cargas usan límites de tamaño y validación de contenido.
- Los secretos de producción se almacenan en Supabase o Vercel, no en Git.
- Los logs evitan nombres, direcciones, correos y contenido documental.
- Se configuran CSP, protección contra framing, `nosniff` y política de referrer.

## 6. Despliegue

### 6.1 Supabase

- Proyecto separado para producción.
- Migraciones aplicadas mediante CLI y CI.
- Auth con correo y contraseña durante el MVP 0.
- Backups y restauración documentados antes de liberar.

### 6.2 Vercel

- El proyecto web se despliega desde `apps/web`.
- Preview deployments utilizan un entorno no productivo cuando exista.
- Las variables públicas y privadas se configuran por ambiente.
- El dominio personalizado es opcional para el MVP 0.

## 7. Decisiones descartadas

### Firebase

No se adopta porque el modelo requiere relaciones, constraints compuestos,
transacciones y autorización alineada con PostgreSQL.

### API NestJS independiente

No se adopta inicialmente porque duplicaría autenticación, autorización,
observabilidad y despliegue. Podrá reconsiderarse si aparecen integraciones o
cargas que justifiquen un servicio persistente.

### Aplicación nativa

No se adopta porque el alcance acordado es una PWA multiplataforma.

### ORM como fuente del esquema

No se adopta durante el MVP 0. Los tipos TypeScript se generarán desde la base de
datos y las migraciones SQL conservarán las capacidades propias de PostgreSQL.

## 8. Variables de entorno

El frontend requiere inicialmente:

```text
NEXT_PUBLIC_APP_URL
NEXT_PUBLIC_SUPABASE_URL
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY
```

Las Edge Functions y la automatización utilizarán secretos administrados por
Supabase. Ningún valor real se documentará o versionará.

## 9. Consecuencias

### Positivas

- Menos infraestructura propia durante el MVP.
- Autorización centralizada y comprobable.
- Modelo relacional portable.
- Preview deployments y ciclos de entrega cortos.
- Un solo lenguaje en la mayor parte del repositorio.

### Costos

- Dependencia operativa de Supabase y Vercel.
- RLS requiere pruebas rigurosas y conocimiento de PostgreSQL.
- Las Edge Functions utilizan un runtime distinto al de Next.js.
- Una futura separación de backend requerirá una migración consciente.
