# Estructura del repositorio

La estructura adoptada para el MVP 0 utiliza un workspace de pnpm. Next.js
contiene la aplicación web y las operaciones HTTP propias del frontend; Supabase
provee PostgreSQL, autenticación, almacenamiento privado y funciones programadas.

```text
gestion-integral-domestica/
├── apps/
│   └── web/                      # Next.js, interfaz y PWA
│       ├── public/               # Iconos y recursos estáticos
│       ├── src/
│       │   ├── app/              # Rutas, layouts y handlers
│       │   ├── components/       # Componentes específicos de la aplicación
│       │   ├── features/         # Casos de uso agrupados por dominio
│       │   ├── lib/              # Integraciones y utilidades de infraestructura
│       │   └── styles/           # Tokens y estilos globales
│       └── tests/                # Pruebas del frontend
├── packages/
│   ├── ui/                       # Sistema de diseño compartido
│   ├── validation/               # Esquemas Zod y reglas reutilizables
│   ├── types/                    # Tipos de dominio y tipos generados de base
│   └── config/                   # Configuración compartida
├── supabase/
│   ├── migrations/               # Esquema, constraints, RLS y funciones SQL
│   ├── functions/                # Edge Functions
│   ├── seed.sql                  # Datos ficticios para desarrollo
│   └── tests/                    # Pruebas de base de datos y políticas
├── Docs/                         # Documentación funcional y técnica
├── .github/workflows/            # Integración continua
├── .env.example                  # Contrato de variables, sin secretos
├── package.json                  # Scripts raíz y workspace
├── pnpm-workspace.yaml
└── README.md
```

## Reglas de dependencia

- `apps/web` puede importar cualquiera de los paquetes compartidos.
- `packages/ui` no conoce Supabase ni reglas de negocio.
- `packages/validation` contiene reglas puras y no depende del framework web.
- `packages/types` no contiene funciones con efectos secundarios.
- El navegador nunca utiliza la service role key.
- Las políticas RLS son la última barrera de autorización; la interfaz no se
  considera una frontera de seguridad.
- Las operaciones que requieren privilegios elevados viven en funciones SQL o
  Edge Functions explícitas y auditables.

No se crea `apps/api` durante el MVP 0. Si una necesidad futura requiere un
servicio independiente, deberá justificarse mediante una decisión de
arquitectura.
